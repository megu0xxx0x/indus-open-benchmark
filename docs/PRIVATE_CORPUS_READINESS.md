# Private corpus readiness audit

`audit-private-readiness` is a local, network-free gate between an ignored
working-data tree and any normalization work. It inventories a physical
owner-only directory, validates a curator-supplied per-file use policy when
present, and produces two deliberately different outputs:

1. a count-free, fixed-vocabulary summary suitable for a terminal or CI log;
2. an optional aggregate report that remains private by default.

Neither output contains a path, filename, source identifier, locator, private
JSON value, sample, or content digest. The scanner uses a fresh in-memory HMAC
key to compare paths and bytes across two complete inventories. Those tokens
are discarded and are never serialized.

`prepare-private-review` is the preceding private curation step. It performs
the same stable double inventory and atomically writes one restricted JSON
bundle containing:

1. an exact-path, exact-byte policy draft in which every use remains denied
   pending curator review; and
2. a path-free structural-quarantine ledger that copies no source value.

Unlike the public summary and aggregate readiness report, that bundle
deliberately contains exact paths and SHA-256 content commitments and therefore
MUST remain `0600`, outside Git, outside any web root, and subject to separate
publication review.

## Scope

`ready=true` means only:

- the same physical tree passed two point-in-time inventories;
- every entry was an owner-only, ACL-free, same-device real directory or
  single-link regular file;
- each file had exactly one private policy entry;
- every policy entry was curator-reviewed and still matched the exact file
  bytes it was reviewed against;
- the declared source was known and did not match the quarantine registry;
- provenance and rights evidence were declared `documented`;
- the content layer and declared rights status were compatible with the
  caller-selected local, non-public use; and
- every recognized content parser completed without an invalid or ragged
  record.

It does **not** establish ownership, legal advice, provenance authenticity,
confidentiality, access history, independent custody, a trusted timestamp,
future immutability, blind evaluation, a decipherment, or prize eligibility.
Those assurance fields are generated by code and remain `false`, including
when `ready=true`.

## Filesystem boundary

Pass the absolute physical storage directory, not the repository's ignored
`data` symlink. The v0.2 readiness contract requires:

- a real absolute path with no symlinked component;
- root and child directories owned by the effective user with mode `0700`;
- files owned by the effective user with mode `0600` and link count one;
- no extended ACL, special file, duplicate inode, or cross-device entry;
- Unicode paths without control characters, traversal components, Unicode
  format controls, or NFKC/case-fold collisions; and
- fixed file, directory, depth, path, byte, JSON, and CSV limits.

Traversal uses pinned directory descriptors, `openat`, `O_NOFOLLOW`, and
pre/open/post fingerprints. It inventories the full tree twice using the same
ephemeral keyed content comparison. A concurrent namespace, metadata, or byte
change fails closed. Mutation after the last check remains possible and is
explicitly not attested.

The scanner reads files only. It performs no network request, decompression,
subprocess execution, data rewrite, duplicate deletion, or automatic
permission repair.

CSV is parsed as strict UTF-8 in a streaming pass with a separate bounded CSV
byte ceiling. Before `csv.reader` can materialize a row, a quote-aware byte
preflight enforces both the logical-record byte limit and the column limit;
the parser pins that same field limit under a module lock and restores the
process-global Python setting afterward. JSON and JSONL retain the smaller
in-memory structured-document ceiling and pass a syntax-, numeric-token-,
node-, and depth-aware preflight before `json.loads` materializes objects.
JSONL record separation is a linear streaming scan. Logical CSV record numbers
are one-based and include the header. Quoted newlines therefore do not change
the record ordinal.

## Private policy

The optional policy follows
[`private-corpus-policy.schema.json`](../schemas/private-corpus-policy.schema.json).
It is a separate `0600` single-link JSON file under a `0700` directory. It
contains one exact `relative_path` entry for every file. Globs, defaults, and
directory inheritance are intentionally unavailable.

Each entry records curator evidence, not a self-declared readiness result:

- `content_sha256`, used only to reject later byte replacement;
- `curation_status`, which must be `reviewed` before readiness is possible;
- `content_layer`;
- `source_id`, plus an optional locator and revision used for quarantine
  matching;
- `provenance_status`;
- `rights_status`;
- `rights_evidence_status`; and
- the exact permitted local, non-public uses.

`restricted` and `unknown` are never compatible. `metadata_only` can cover
only metadata, documentation, derived statistics, or configuration. A
declared permission is still not independently authenticated by this tool.
A digest match establishes neither rights nor provenance and supplies no
trusted timestamp, custody, authorship, or confidentiality evidence.

Without a policy, the scanner can produce a structural aggregate, but it must
return `RIGHTS_COVERAGE_INCOMPLETE` and `ready=false`.

## Deny-all review bundle

`prepare-private-review` generates a policy v0.2 draft with the following
fixed defaults for every file:

```json
{
  "curation_status": "pending",
  "content_layer": "unknown",
  "source_id": "unresolved-private-source",
  "source_locator": null,
  "source_revision": null,
  "provenance_status": "unknown",
  "rights_status": "unknown",
  "rights_evidence_status": "missing",
  "permitted_uses": []
}
```

It never guesses source, content layer, provenance, or rights from a filename,
extension, embedded value, or public availability. Generation succeeding does
not permit research or normalization. The independent `pending` gate remains
blocking even if the placeholder source identifier were later added to a
registry.

The embedded structural ledger follows
[`private-structural-quarantine.schema.json`](../schemas/private-structural-quarantine.schema.json).
It refers to the matching policy entry by zero-based index and repeats only the
private byte commitment, not the path. An anomaly contains a closed code,
optional one-based logical record number, and optional expected/observed column
widths. It contains no cell, header, row, source/catalog identifier, sample,
or exception text. Its private content digest and internal policy index are
explicitly declared by the schema. Clean files are omitted. Duplicate-content
files remain unambiguous because their policy indices differ.

The ledger has `source_data_modified=false` and `readiness_override=false`.
Recording an anomaly never repairs, removes, normalizes, or authorizes the
source. In particular, a raw ragged CSV remains
`CONTENT_CONTRACT_INVALID`; only a separately derived, content-bound,
rights-compatible normalization can later be evaluated.

The two documents are published as one
[`private-review-bundle.schema.json`](../schemas/private-review-bundle.schema.json)
envelope. A descriptor-pinned, exact-byte, ACL-free, no-replace writer commits
the single `0600` file atomically, verifies the requested path, and fsyncs the
parent directory. Existing regular files, links, directories, and special
entries are never replaced. A post-commit uncertainty is reported distinctly
and MUST NOT trigger an automatic retry. The supported CLI flow publishes only
the in-memory bundle returned by its immediately preceding scan and rechecks
the physical root identity. A bundle returned by the reader lacks that
non-serialized identity and cannot be passed directly to the writer. The
public Python data class is not an unforgeable provenance token, so custom API
callers remain responsible for preserving this same build-then-publish flow.

If a structured document exceeds a byte, logical-record, row, column,
numeric-token, node, depth, or anomaly-enumeration limit, the analysis is
incomplete and bundle generation fails closed without publishing a partial
ledger.

## CLI

Create all parents separately with owner-only permissions. The review bundle
and report must both be outside the corpus root.

```bash
install -d -m 700 /private/reviews /private/reports

uv run indusbench prepare-private-review \
  /private/physical-corpus-root \
  /private/reviews/review-bundle.json \
  --created-at 2026-07-27T08:00:00Z

uv run indusbench audit-private-readiness \
  /private/physical-corpus-root \
  --intended-use local_nonpublic_normalization \
  --created-at 2026-07-27T08:00:00Z \
  --policy-bundle /private/reviews/review-bundle.json \
  --private-report /private/reports/readiness.json
```

The generated bundle remains blocked until every entry has been supported by
curator evidence and explicitly changed to `curation_status: reviewed` with
compatible fields. `--policy /private/policies/corpus-policy.json` remains
available for a separately maintained v0.2 policy. `--policy` and
`--policy-bundle` are mutually exclusive. The checked-in source and quarantine
registries are used by default; explicit alternatives are available for
controlled testing. A policy or bundle located inside the corpus is rejected.

The report writer is atomic and no-replace. An existing destination is never
overwritten. The created file uses mode `0600`.

Exit codes:

- `0`: the declared local use is ready at the checked point in time;
- `2`: a completed scan is blocked, or an input/output failure was safely
  normalized to a fixed reason code;
- argument parsing errors retain the normal CLI behavior.

For `prepare-private-review`, `0` means only that the deny-all bundle was
committed and verified. Unsafe input/output, an empty corpus, concurrent
mutation, artifact-limit failure, an existing destination, or uncertain
publication returns `2`. Its count-free summary always says
`corpus_use_permitted=false` and `curator_review_required=true`.

The terminal summary is governed by a closed allowlist:

```json
{
  "schema_version": "0.2.0",
  "claim_class": "private_working_corpus_readiness",
  "intended_use": "local_nonpublic_normalization",
  "ready": false,
  "scan_completed": true,
  "reason_codes": ["RIGHTS_COVERAGE_INCOMPLETE"],
  "assurance": {
    "blind_claim_allowed": false,
    "final_evaluation_eligible": false,
    "independent_custody_attested": false,
    "external_custodian_attested": false,
    "trusted_timestamp_attested": false,
    "access_history_attested": false,
    "confidentiality_attested": false,
    "rights_ownership_attested": false,
    "provenance_authenticity_attested": false,
    "future_immutability_attested": false,
    "decipherment_claim_allowed": false,
    "prize_submission_eligible": false
  }
}
```

The aggregate report follows
[`private-corpus-readiness.schema.json`](../schemas/private-corpus-readiness.schema.json).
It adds only counts for inventory, fixed format classes, exact duplicate
groups, policy statuses, and declaration coverage. Treat it as private until a
separate disclosure review determines that even those aggregates are safe to
publish.

## Fixed failure vocabulary

The summary can emit only schema-enumerated reason codes. Filesystem and
parser exception text is never forwarded because it can quote a private path
or value. The principal groups are:

- platform, root, permission, ACL, namespace, link, device, path-profile, and
  mutation failures;
- resource or input-verification failures;
- malformed policy, incomplete coverage, pending review, or byte-binding
  mismatch;
- ambiguous rights, incompatible use, or unknown/quarantined source; and
- invalid content contract or an internal fail-closed condition.

Detailed remediation belongs in the private review workflow, not in public
logs.
